# 動作条件

お使いの環境で動くかどうか。そして Linux について、うまく動かなかったときのために一つだけ知っておいてほしいことがあります。

英語版は [docs/requirements.md](../requirements.md) です。

## Windows

| | |
|---|---|
| **Windows 10 / 11** | マスコット、トレイアイコン、コマンドライン |
| **Windows 11** | …に加えて、Fluent デザインのトレイメニューと設定ウィンドウ |

必要なものは他にありません。.NET ランタイムも再頒布可能パッケージも不要です。`dragonperch.exe` は 2MB ほどの Win32 プログラムで、必要なものはすべて内側に入っています。

Fluent 側は独立したプログラムで、入れるかどうかは自由です（何者なのか、なぜ別プロセスなのかは [実行のしかた](running.md) にあります）。Windows 11 を要求するのは、Segoe UI Variable をはじめ Fluent 2 が前提とするものが Windows 11 で揃ったからです。

入れない場合に出るのはデーモン自身の Win32 メニューで、見た目が違うだけで、できることは変わりません。**設定** はシェルが入っていれば同じウィンドウを開き、入っていなければ淡色表示になります。マスコットもトレイアイコンもコマンドラインもそのままです。

実際に動作を確認しているのは Windows 11 のみです。デーモンのマニフェストは Windows 10 も宣言しており、11 でなければ動かない部分はありません。

## Linux

**Wayland のみ**で、コンポジタが別々の2つの機能を提供している必要があります。

| | オーバーレイ | ウィンドウの位置 | |
|---|---|---|---|
| **KDE Plasma 6（Wayland）** | ✔ layer shell | ✔ KWin スクリプト | すべて動きます |
| wlroots 系（Sway、Hyprland） | ✔ layer shell | ✘ 未実装 | マスコットは出ますが、画面の下端しか歩けません |
| GNOME（Mutter） | ✘ layer shell 非対応 | — | 起動しません |
| X11（デスクトップ環境を問わず） | — | — | 対象外です |

**オーバーレイ**には `zwlr_layer_shell_v1` が必要です。wlroots 系のコンポジタはすべて実装しており、KWin も実装しています。一方 Mutter は採用を見送っており、Wayland の画面全体にクリックが透過する面を重ねる方法は他にありません。無い場合、DragonPerch は何も描かないまま黙っているのではなく、エラーを出して止まります。

**ウィンドウの位置**のほうが難しく、このプログラムの形を決めているのもこちらです。Wayland のクライアントは、他のクライアントのウィンドウがどこにあるかを知ることを許されていません。教えられるのはコンポジタの内側にいる誰かだけで、Plasma ではそれが後述の KWin スクリプトです。Sway と Hyprland は `swaymsg` や `hyprctl` で答えられるはずですが、まだ誰も書いていません。GNOME であれば Shell 拡張が必要になります。

どれも無い環境でもマスコットは動きます。ただ、画面の下端以外に立つ場所がないというだけです。デーモンはそれに気づくと、ログにそう書きます。

X11 を対象にしないのは意図的です。ワールドプロバイダをもう1つ抱えることになり、フレームクロックはより不利なものになり、これ以降のすべての機能を運び続ける3つ目のプラットフォームが増えます。しかもその相手は、Plasma が畳もうとしているセッション形式です。理屈は[計画](../plan.md)に書いてあります。

## KWin スクリプト

ドキュメントが以前に間違えていたのがここなので、正確に書きます。

**普段の利用では、インストールも有効化も必要ありません。** DragonPerch は起動するたびに自分でスクリプトを探し出し、セッションバス上の KWin のスクリプティング機能を通じて「これを実行してほしい」と依頼します。探す順番は次のとおりです。

1. 実行ファイルから見た `../share/kwin/scripts/`（tar.gz を展開した場合。`/usr/bin` にあるパッケージ版なら `/usr/share`）
2. `$XDG_DATA_HOME/kwin/scripts/`（`kwin/install.sh` が置く場所）
3. `/usr/share/kwin/scripts/` と `/usr/local/share/kwin/scripts/`
4. 実行ファイルから上に遡ったソースツリー（チェックアウトしたリポジトリのビルドディレクトリ）

つまり、`dragonperch-kde` パッケージは入れた時点で動き、tar.gz は展開した場所でそのまま動き、ビルドしたばかりのチェックアウトもそのまま動きます。ログに `kwin: asked it to re-run …` と出ていれば成功しています。

この順序でなければならない理由もあります。KWin スクリプトは、コンポジタが読み込んだときに一度だけ走る文の並びです。読み込まれるのはログイン時、つまり DragonPerch がまだ存在しない時点であり、それ以降はウィンドウが変化したときにしか喋りません。そこで、クライアント側が聞く体勢を整えたうえで、コンポジタに「もう一度走らせてほしい」と頼むことにしています。

### では、システム設定のチェックボックスは何のためにあるのか

> システム設定 → ウィンドウ管理 → KWin スクリプト → *DragonPerch geometry*

ここを有効にすると、DragonPerch が動いているかどうかに関係なく、**KWin 自身が**ログイン時にスクリプトを読み込むようになります。必須ではなく、いわば保険です。デーモンが起動してから読み込まれるのではなく、起動した時点ですでにスクリプトが喋っている状態になります。

`dragonperch-kde` パッケージがこれを有効にしないのは意図的です。メタデータには `EnabledByDefault: false` と書いてあり、パッケージが `kwinrc` に何かを書き込むこともありません。何かの依存関係で勝手に入ってきただけのプログラムが、ユーザーのコンポジタの内側でコードを走らせ始めたら、どんな目に遭っても文句は言えません。

`kwin/install.sh` は、チェックアウトから同じことを行うためのものです。スクリプトを `~/.local/share/kwin/scripts/` にコピーし、`kwinrc` に項目を書いてチェックを入れ、ログインし直さずに反映されるよう KWin にスクリプティングの再読み込みを依頼します。これはリポジトリの中にあるもので、tar.gz には含まれていません。そして、DragonPerch を動かすだけなら実行する必要はありません。

### install.sh を実行した後にパッケージを入れた場合

コピーが2つになりますが、2つの読み込み側が選ぶものは同じではありません。DragonPerch はまず自分の実行ファイルの隣を見るので、`/usr/bin` にあるパッケージ版はパッケージ側のコピーを掴みます。一方 KWin 自身はホームディレクトリ側を優先するので、ログイン時に走るのはそちらで、DragonPerch が起動して差し替えるまでその状態が続きます。開発中はそれで正しく、アップグレード後は間違っています。デーモンはどちらか一方を黙って選ぶのではなく両方の場所を挙げますし、答えてきたスクリプトの報告フォーマットが食い違っていれば、そのことも知らせます。パッケージを更新したのに何も変わっていないように見えるなら、原因はこれです。

```bash
rm -rf ~/.local/share/kwin/scripts/dragonperch-geometry
```

### 喋っているかどうかを確かめる

```bash
dragonperch-wl --dump-world --hold
```

ウィンドウをドラッグして、数値がタイトルバーを追いかけるかどうかを見てください。追いかけていれば、難しいほうの半分は動いています。`--dump-world` は診断用のため、リリースビルドには入っていません。診断機能を残したままリリースビルドを作る方法は [実行のしかた](running.md) にあります。スクリプト自身の出力は、コンポジタのジャーナルに出ます。

```bash
journalctl --user -f -t kwin_wayland
```
