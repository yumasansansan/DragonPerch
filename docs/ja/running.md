# 実行のしかた

コマンドライン、トレイアイコン、診断モードについて説明します。設定の変更方法については [設定](settings.md) を参照してください。

英語版は [docs/running.md](../running.md) です。

## 動かしてみる

```bash
dragonperch --pets 6
dragonperch --pause
dragonperch --stop
```

Linux では、ウィンドウの位置情報はコンポジタから受け取ります。その段取りは DragonPerch が自分で済ませるので、先に何かをインストールしたり有効にしたりする必要はありません。起動のたびに KWin スクリプトを探し出し、KWin に実行を依頼します。どこを探すのか、どのコンポジタなら動くのか、`kwin/install.sh` は何のためにあるのかは、[動作条件](requirements.md)をご覧ください。

`--pets N` は**各**マスコットを何体表示するかを指定するオプションで、設定ファイルの `pets-per-mascot` の値を一時的に上書きします。
既定値は各1体なので、同梱されている3種類のマスコットでは合計3匹になります。

## トレイアイコン

トレイアイコンは両方のプラットフォームにあり、DragonPerch を終了する通常の手段でもあります。右クリックで「一時停止」「設定」「終了」が選べます。
Windows では `Shell_NotifyIcon`、Linux では StatusNotifierItem を使用します。後者はメニューを「描画する」のではなく「書き並べてコンポジタに渡す」仕組みで、受け取った Plasma が Breeze のメニューを組み立て、ユーザーのテーマに合わせてくれます。こちら側に描画のコードは一行もありません。

Windows のメニューは本格的な WinUI 3 の `MenuFlyout` を使っており、`shell/windows/` にある別のプログラム `DragonPerch.Shell.exe` が描画を担当します。これを別プロセスに分けたのには、実際に計測した上での明確な理由があります。XAML を初期化すると、プロセスは恒久的に約50MBのプライベートメモリを消費し、閉じても解放されないからです。そこで、ツールキットは必要になったときだけ起動し、マスコットたちに気づかれずにいつでも落とせる場所へ隔離することにしました。これにより、`dragonperch.exe` 本体は Windows App SDK とは無縁の、わずか 2MB の軽量な Win32 プロセスのまま維持されています。

デーモンは、マウスポインタがトレイアイコンに重なった瞬間にシェルを裏で起動し始めます。コールドスタートの WinUI プロセスが実際にボタンを押されるまでに必要な数百ミリ秒を、そこで先回りして稼ぐのです。シェルが入っていない、起動が間に合わない、落とされてしまった、のいずれの場合でも、デーモン自身の `TrackPopupMenuEx` による軽量なメニューを即座に表示します。絶対に待ちません。クリックから0.5秒も遅れて表示されるメニューは、ユーザーにはハングアップしているように見えてしまうからです。**シェルは文字通り完全に「オプション」です。** ディスク上に影も形もなくても、デーモンは完全に正常動作します。

## 診断モード

```bash
dragonperch --dump-world --hold
dragonperch --probe-composition --hold
```

`--dump-world` は、新しいマシンの Linux でまず試すべきコマンドです。KWin が通知してきた内容を標準出力にダンプするだけで、レンダラーは一切起動しません。ウィンドウをドラッグしたときに画面上の数値が追従するなら、難しい半分（ウィンドウ位置の取得）は動いている証拠です。それでも画面表示がおかしいなら、それはレンダラー側の問題だと切り分けられます。

**診断モードは Debug ビルド限定です。** `--probe-composition`、`--dump-world`、`--self-test`、`--export-placeholder` といったオプションはリリースビルド（パッケージ版や nightly 版）からは完全に削除されます。
しかし、これらは無駄なコードではありません。このプロジェクトで遭遇した難しいバグは、すべてこれらの機能によって解決されてきました。そのため、この機能のオンオフはビルド構成（Debug/Release）とは別のスイッチとして独立しています。

```bash
cmake --preset windows-x64 -D DRAGONPERCH_DIAGNOSTICS=ON
```

こうすることで、診断機能が有効になった「リリースビルド」が得られます。出荷版のバイナリがユーザーの手元で不具合を起こしたときにビルドすべきなのは、これです。Debug ビルドは実行タイミングも Direct2D の挙動も異なるため、バグ調査の答えが変わってしまうことがあるからです。

## 制御インターフェース

`--stop`、`--pause`、`--resume`、`--reload` などのコマンドは、すべて1つの制御インターフェースを通じて処理されます。Windows では `WM_COPYDATA` を受け取るメッセージ専用ウィンドウ、Linux ではセッションバス上の `org.dragonperch.Control` です。
どちらも専用のスレッドを必要としません。Windows ではオーバーレイ用のメッセージループがすでに回っており、Linux では KWin のレポートを受け取るバスの処理がすでに動いているからです。トレイアイコンや設定プログラムも、同じインターフェースを通してこれら4つのコマンドを呼び出しているだけです。

`--stop` オプションが存在する理由は、Windows では `Ctrl+C` が「ほぼ効く」ものの、完全には当てにできないからです。DragonPerch は GUI サブシステムのバイナリとしてビルドされているため、コマンドプロンプトはプログラムの終了を待たずにすぐに戻ってしまいます。そのプロンプトで打ち込んだ `Ctrl+C` がコンソールイベントとして飛ぶかどうかはシェル次第です。`cmd` は送ってくれますが、PowerShell 7 は送りません（PSReadLine がキーを奪ってしまうためです）。なお、コンソールウィンドウ自体を閉じる方法は確実に効きます。Linux では `Ctrl+C` が正常に効きます。

一時停止すると、シミュレーションと描画が止まり、オーバーレイは最後のフレームを映したまま残ります。再開のたびに作り直す実装にしなかったのは、ウィンドウとサーフェスの初期化コードをもう一度通ることになるからです。そこはこのプログラムで最もバグを作り込みやすかった鬼門でした。

## ログ

診断情報は標準出力**と**実行ファイルと同じフォルダの `dragonperch.log` の両方に出力されます。GUI サブシステムで動くバイナリは、常にコンソール（標準出力）が見える状態にあるとは限らないためです。
