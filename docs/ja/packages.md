# パッケージとダウンロード

英語版は [docs/packages.md](../packages.md) です。

`main` ブランチのビルドごとに、常に最新の **`nightly`** プレリリースが公開されます。また、CI が実行されるたびに同じファイルがアーティファクトとして14日間保存されます。どちらも同じ `install()` ルールから生成されるため、テストされたものと全く同じものが配布される仕組みです。

| ファイル | 使い方 |
|---|---|
| `dragonperch_0.1.0~…_amd64.deb` | `sudo apt install ./dragonperch_*.deb` |
| `dragonperch-kde_0.1.0~…_amd64.deb` | Plasma 専用: KWin スクリプトと KDE 設定モジュール |
| `dragonperch_0.1.0~…_x86_64.tar.gz` | 任意の場所に展開し、`usr/bin/dragonperch-wl` を実行 |
| `dragonperch_0.1.0~…_x64.zip` | 展開して `dragonperch.exe` を実行 |

## バージョンの規則

nightly ビルドは、バージョン番号にビルド日時とコミットハッシュを含みます。これにより、`apt` は古いファイルへのダウングレードとして拒否するのではなく、次の nightly へ正しく**アップグレード**してくれます。

これを可能にしているのが **チルダ (`~`)** です。Debian のパッケージシステムでは、`~` は「何よりも前（文字が存在しないことよりも前）」にソートされるという特殊なルールがあります。

```
0.1.0~20260828.1830.g462431a  <  0.1.0~20260829.0300.gdeadbee  <  0.1.0
```

つまり、nightly ビルドは昇順に並び、本物の `0.1.0` のリリースが来ればすべての nightly を綺麗に上書きできるようになっています。`dragonperch --version` を実行すれば、インストールされているバージョンを正確に確認できます。

なお、**ダウンロードしたファイル名では `~` が `.` に変換されています。**
これは、GitHub がリリース資産（Release Asset）のファイル名から `[A-Za-z0-9._-]` 以外の文字を書き換えてしまうためです。しかし実害はありません。`dpkg` や `apt` はパッケージ内部の `control` フィールドからバージョンを読み取るため、ファイル名は単なる慣習であってデータではないからです。ご自身で確認することもできます：

```bash
dpkg-deb -f dragonperch_*.deb Version
```

CI でも毎回この `control` フィールドを表示し、`dpkg --compare-versions` を使って「リリース版より前にソートされること」をテストしています。もしこの規則が壊れた場合はビルドが失敗するようになっています。

## Debian では2つ、それ以外は1つ

Debian 向けのパッケージは2つに分かれています。
`dragonperch` には、デーモン本体、アートワーク、翻訳、デスクトップエントリが含まれており、KWin についての知識は一切持っていません。
一方 `dragonperch-kde` は Plasma 専用のもので、KWin スクリプトと設定モジュールが含まれています。こちらは対応するバージョンの `dragonperch` に厳密に依存しており、デーモン側からもこれを `suggests` (推奨) することで、Plasma 環境へのインストール時に必要なもう半分をユーザーに提案するようになっています。

パッケージを分けた理由は、現在の実装のためというよりも**今後の展開**を見据えてのことです。KWin 以外の環境（GNOME の Shell 拡張や、wlroots の `swaymsg` / `hyprctl` など）に対応する場合、それぞれが固有の依存関係を引き連れてきます。世の中に存在するデスクトップ環境の数だけ Recommends が無駄に膨れ上がっていくような単一パッケージは避けるべきだからです。

一方で、tar.gz（tarball）は**意図的に分割していません**。「展開してすぐ動く」ことこそがその存在意義であり、ユーザーに2つのアーカイブを正しい順序で展開させるのは本末転倒だからです。

アートワークは実行ファイルからの相対パスで探されるため、tarball を展開した場合はインストールしなくても、環境変数なしでそのまま動きます。
なお、パッケージをインストールしただけでは KWin スクリプトは**有効化されず、ログイン時の自動起動も行われません**。何かの依存関係で勝手に入ってきたプログラムが、ユーザーの画面に突然マスコットを出現させるような行儀の悪いことはしません。

## Windows Defender がダウンロードを検知する

ダウンロード時に `Trojan:Win32/Wacatac.B!ml` といった警告が出ることがあります。手がかりは末尾の `!ml`（Machine Learning）です。これはシグネチャの一致ではなく、機械学習による推測であることを示しています。

これは誤検知であり、予測できた事態でもあります。このバイナリは未署名で、ビルドされたばかりで、まだ誰にもダウンロードされておらず、その上「他のアプリケーションのウィンドウを列挙し、システム全体のイベントフックを仕掛け、画面全体を覆う透明な最前面ウィンドウを維持する」という、いわゆる画面収集ツール（スクリーン・スクレイパー）とほぼ同じ振る舞いをします。

この警告を消すための魔法のような小細工はありませんし、もしあるとすればそれ自体が疑わしいものです。本当の解決策は以下の2つしかありません。

- <https://www.microsoft.com/en-us/wdsi/filesubmission> から**誤検知として報告する**。これは非常に効果的であり、やる価値があります。あなただけでなく、全員に対して検知されなくなるからです。
- **コード署名を行う。** コード署名証明書はバイナリに身元を与え、評判を蓄積させるためのものです。署名がない限り、新しいビルドのたびに信頼度はゼロからのスタートとなり、Defender が警告しなくても SmartScreen が警告を出します。

ご自身でソースからビルドした場合は、インターネットからダウンロードしたファイルではないため、この問題は発生しません。

自分でビルドするには以下のようにします：
```bash
cmake --build --preset linux-x64-release && cd build/linux-x64 && cpack -C Release
```
