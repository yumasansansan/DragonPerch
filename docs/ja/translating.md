# DragonPerch を翻訳する

英語版は [docs/translating.md](../translating.md) です。

**文字列テーブルはプロジェクト全体で1つだけ**です。ここにはプログラムが3つ（デーモン、Windows シェル、KDE 設定モジュール）ありますが、仕組みを3つ持てば同じ文を3回訳すことになり、その3つが別々の方向へずれていきます。

動かすために何かをインストールする必要はありません。呼び出し側のコードが英語の原文を持っていて、それがそのままフォールバックになります。`lang` ディレクトリが一つも無いビルドでも、この仕組みが入る前と一字一句同じ英語が表示されます。

## 言語を追加する

`lang/ja.ini` をコピーし、ファイル名を目的の言語タグに変更して、右辺を翻訳します。

```ini
[Strings]
menu.pause = Pausa
menu.quit = Chiudi DragonPerch
```

ファイルの配置場所は、実行ファイルと同じディレクトリの `lang/` か、インストール済みの環境であれば `share/dragonperch/lang` になります。アートワークを探すのと同じ規則なので、書庫を展開しただけのポータブルな状態でもそのまま機能します。

たとえば `ja.ini` というファイル名は、`ja` や `ja-JP` など、`ja-` で始まるすべての言語設定に対して使われます。もし特定の地域で独自の表現が必要な場合は `pt-br.ini` のようにし、そうでない場合は `pt.ini` にします。より具体的（長く一致する）ファイル名が優先されます。

**ファイル名はすべて小文字で、ハイフンを使います。** システムが報告してくる言語設定は、ファイルを探す前にあらかじめ正規化されます（`ja_JP.UTF-8` も `ja-JP` もすべて `ja-jp` として扱われます）。もし `pt-BR.ini` という大文字混じりの名前をつけてしまうと、「Windows では見つかるのに Linux では見つからない」という最悪の壊れ方をします。

翻訳されていないキーは、自動的に英語へフォールバックされます。そのため、**部分的な翻訳でも十分に有用です**。すべてを完璧に翻訳し終えるまで公開できない、ということはありません。

ただし、1つだけ知っておくべき制約があります。翻訳文の中に半角の `;` や `#` は使えません。どちらのパーサ（C++とC#）も、これらをコメントの開始とみなして行をそこで打ち切ってしまうからです。これらの記号が必要な言語では、全角の `；` や `＃` が用意されているはずですし、そもそも日本語の文章であれば自然とそちらを使うでしょう。

## なぜキーが英語ではなく id なのか

`menu.pause = 一時停止` であり、`Pause = 一時停止` ではありません。

理由は2つ、どちらも実務的なものです。1つは、このファイルが INI であり、英文には `=` や `;`、`#` が普通に出てくるからです。この形式では、そのどれもが区切りやコメントとして読まれてしまいます。
もう1つは、英語のほうを書き直すことがよくあるからです。英文そのものをキーにしていると、少し言い回しを変えただけで、**その文に対するすべての言語の訳が黙って外れます**。症状として現れるのは、画面の半分だけが別の言語になっている状態だけです。

この設計の代償として、呼び出し側のコードでは文字列を2回指定する必要があります。

```cpp
tr("menu.pause", "Pause")
```

しかし、これこそが「英語のカタログファイルをわざわざインストールしなくてもフォールバックが機能する」理由でもあります。

## どこに何があるか

| | |
|---|---|
| `src/core/dragonperch/language.hpp` | 文字列テーブル本体と `tr` 関数 |
| `lang/*.ini` | 翻訳カタログ |
| `src/win/tray.cpp`, `src/linux/tray.cpp` | トレイメニューの実装 |
| `shell/windows/Strings.cs` | Windows シェル側で同じカタログを読み込む処理 |
| `shell/windows/TrayMenu.cs`, `SettingsWindow.xaml.cs` | Fluent メニューと設定ウィンドウ |
| `kcm/` | KDE 設定モジュール（QML 内で `kcm.text(id, english)` として使用） |

Windows の設定ウィンドウでは、コード内に英語の原文を二重に持たせることはせず、**XAML マークアップ内に書かれたテキストをそのままフォールバックとして利用しています**（例: `Strings.Get("settings.pets", PetsTitle.Text)`）。これにより、英語の原文が存在する場所を1箇所に保ちつつ、もし翻訳されていない id があっても、マークアップに記述された要素がそのまま崩れずに表示されます。

どの言語を使うかは、各プログラムが OS に直接尋ねて決めます。コアがそれをすることは許されていないからです。Windows では `GetUserPreferredUILanguages`、Linux では `LC_ALL` / `LC_MESSAGES` / `LANG` をこの優先順で、Windows シェルでは `CultureInfo.CurrentUICulture`、KDE 設定モジュールでは `QLocale::system().uiLanguages()` を見ます。

どちらのプラットフォームでも、見ているのはロケールではありません。ロケールは数字や日付の見た目を決めるもの、UI 言語は表示される単語そのものを決めるもので、どちらのシステムでも別々に設定できます。`LC_ALL=C` と `LANG=ja_JP.UTF-8` が同居していれば、UI は英語になるのが正解です。これは実際に確認してあります。
どの言語カタログが読み込まれ、いくつの文字列がロードされたかは、`dragonperch.log` に記録されます。
